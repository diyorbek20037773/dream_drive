# Detector accuracy evaluation

This page documents how DreamDrive measures object-detector accuracy, on what data, with which results, and what is
**not** evaluated. Every number below is copied from an Evaluation JSON produced by the commands in
[How to reproduce](#how-to-reproduce); nothing is estimated or taken from upstream papers.

## What is measured

| Item | Value |
|---|---|
| Evaluation kind | `video_ml_accuracy` (listed by `GET /api/v1/evaluations` when the JSON is in the evaluations directory) |
| Source | `learned_model`: real checkpoints through the production inference service |
| Data | COCO val2017 street-scene subset `coco_val2017_street_v1` (300 images; rule below) |
| Path | image JPEG → RGB → JPEG quality 95 (same encoder as `app/video/pipeline.py`) → `InferenceClient.infer` → `POST /v1/infer?conf_threshold=0.1&include_masks=true` |
| Protocol | COCO bbox AP: IoU 0.50:0.05:0.95, 101-point interpolation, maxDets 100 per image and class, area `all`, `iscrowd=1` boxes are ignore regions |
| Implementation | `backend/app/evaluation/coco_ap.py` (NumPy), cross-checked against `pycocotools` (`tools/eval`) |
| Confidence threshold | 0.1, the production default (`INFERENCE_CONF_THRESHOLD`); see limitations |

### Class mapping (docs/IMPLEMENTATION_SPEC.md 2.1)

Detections are mapped by `class_name`. Only classes the running service declares in its class maps are scored; a class
the service does not output is reported as `unsupported` (value `null`), never as 0.

| Eval class | Service `class_name`(s) counted as predictions | COCO ground-truth categories | Model |
|---|---|---|---|
| `person` | `person` | person | RF-DETR-N |
| `bicycle` | `bicycle` | bicycle | RF-DETR-N |
| `motorcycle` | `motorcycle` | motorcycle | RF-DETR-N |
| `bus` | `bus` | bus | RF-DETR-N (includes boxes that replaced a YOLOPv2 vehicle box) |
| `truck` | `truck` | truck | RF-DETR-N (includes boxes that replaced a YOLOPv2 vehicle box) |
| `traffic_light` | `traffic_light` | traffic light | RF-DETR-N (box only; colour is a heuristic) |
| `stop_sign` | `stop_sign` | stop sign | RF-DETR-N |
| `vehicle` | `vehicle` | car + bus + truck (merged) | YOLOPv2, cross-dataset check |
| `vehicle_any` | `vehicle`, `bus`, `truck` | car + bus + truck (merged) | ensemble output as drawn by the app |

`map50_enabled_classes` / `map50_95_enabled_classes` are the unweighted means over the seven RF-DETR classes enabled in
DreamDrive (first seven rows); their `sample_count` is the sum of those classes' GT instances. `vehicle` and
`vehicle_any` are reported separately because COCO and BDD100K label vehicles differently.

Metric names in the Evaluation JSON: `ap50_<class>`, `ap50_95_<class>`, `recall50_<class>` (unit `ratio`,
`sample_count` = non-crowd GT instances of that class), `inference_latency_p50_ms` / `_p95_ms` (service
`timing_ms.total`), `request_roundtrip_p50_ms` / `_p95_ms` (client wall time incl. mask PNGs and JSON),
`images_evaluated`, and `lane_accuracy`, `drivable_area_iou`, `traffic_light_colour_accuracy` (`not_evaluated`).
Per-class details (AP75, mean recall over thresholds, images with GT, detections scored, recall per IoU threshold),
dataset hashes, model identities and host information are in the JSON file's `details` block; the API
(`GET /api/v1/evaluations`, `GET /api/v1/evaluations/{id}`) returns the metrics, limitations and identities without it.

## Data: subset rule, counts and licences

Source: `annotations/instances_val2017.json` (SHA256 `e8c7f790…10b6f`) read directly from the verified archive
`annotations_trainval2017.zip` (SHA256 `113a836d90195ee1f884e704da6304dfaaecff1f023f49b6ca93c4aaae470268`). Neither the
archive nor any image is committed; see docs/DATA_SOURCES.md, section "COCO val2017 evaluation subset".

Rule (deterministic, `select_street_subset` in `backend/app/evaluation/detector_accuracy.py`): an image qualifies when it
has at least one **non-crowd** instance of {traffic light, stop sign, person} **and** at least one non-crowd instance of
{car, bus, truck, motorcycle, bicycle}. Crowd annotations never qualify an image, so crowd-only images are excluded.
Qualifying ids are sorted ascending and the first 300 are taken. 656 val2017 images qualify; ids 724 … 278705 are used.
The manifest `datasets/manifests/coco_val2017_street_v1.json` (SHA256
`3bf25c874c88d01db8b7111064d3d84c3c06554bf809443298aa967a02cf4572`) is regenerated byte-identically from the archive.

Ground-truth instances in the 300 images (from the manifest):

|---|---|---|---|
| person | 1522 | 42 | 275 |
| bicycle | 138 | 0 | 62 |
| car | 674 | 5 | 189 |
| motorcycle | 171 | 3 | 67 |
| bus | 104 | 1 | 67 |
| truck | 139 | 0 | 91 |
| traffic light | 217 | 2 | 60 |
| stop sign | 16 | 0 | 14 |

Merged car+bus+truck (eval classes `vehicle`, `vehicle_any`): 917 non-crowd instances in 242 images.

Licences: annotations CC BY 4.0 (COCO Consortium). Images keep their Flickr licences, recorded per image in the
manifest: by-nc-sa 2.0 (100 images), by-nc 2.0 (39), by-nc-nd 2.0 (68), by 2.0 (50), by-sa 2.0 (25), by-nd 2.0 (18).
Images are downloaded on demand from `images.cocodataset.org` for local evaluation only; each file's SHA256 is pinned in
`<cache>/cache_index.json` on first download and verified on later runs.

The latency figures were measured while three other inference containers (`dd-kitti`, `dd-video-e2e2`,
`dd-rfdetr-gpu-offline`) shared the CPU, so they overstate the uncontended CPU latency. For comparison, the detector
engineer's model smoke (`artifacts/qa/spike/rfdetr/model_smoke_cpu.json`, the 1280x720 YOLOPv2 example frame, 20 timed runs) recorded a combined
engine forward p50 of 450 ms (YOLOPv2 313 ms); that is a different input and load, not this evaluation's number.

Observations (facts from the raw predictions, `artifacts/qa/spike/c77b30763a37492888f68c3f9e794d6d.predictions.json`):

- YOLOPv2 produced the same 1511 `vehicle` boxes as in the single-model dry run below; ensemble class refinement
  relabelled 350 of them (257 → `truck`, 93 → `bus`, `refined_from_model = "yolopv2"`), leaving 1161 `vehicle` boxes.
  The subset contains 139 COCO trucks and 104 buses, so many relabelled boxes are scored as wrong-class `truck`
  predictions while the corresponding COCO `car` is missed by `vehicle`. This is why `vehicle` AP50 here (0.3635) is far
  below YOLOPv2 alone (0.6805, dry run) and `truck` AP50 is 0.5075. `vehicle_any` (0.6356) is what the app draws.
- Some images have more than 100 `person`/`motorcycle` detections at threshold 0.1; COCO maxDets=100 per image and
  class drops the lowest-scored ones (7023 → 7016 person, 812 → 721 motorcycle scored).

### Validation run (not the release measurement): YOLOPv2 only

Before the two-model image existed the whole flow was validated against the previous single-model image
(`dreamdrive-inference:dev`, short id `f94c7639c555`, YOLOPv2 only), labelled `dry_run_single_model_yolopv2`
(evaluation `7887d5d85bce4e4d89549451f8d45f38`, stored under `artifacts/qa/spike/detector_accuracy_dryrun/` so the API
does not list it). Same 300 images (identical pinned image-hash list). RF-DETR classes were correctly reported as
`unsupported`. YOLOPv2 `vehicle` vs COCO car+bus+truck: AP50 **0.6805**, AP50:95 **0.4611**, AP75 0.5030,
recall@0.50 0.7525 (917 GT instances, 1511 detections). Service latency p50 516.7 ms / p95 1015.1 ms (300 images,
CPU, also under concurrent load). This isolates YOLOPv2 before ensemble refinement; it is not the shipped configuration.

## Numerical cross-check against pycocotools

`tools/eval` is a separate uv project (Python 3.11, `numpy` 2.4.6, `pycocotools` 2.0.11, locked in `tools/eval/uv.lock`).

- `random_crosscheck.py`: 20 randomised trials (seed 20261010; 2,482 GT boxes incl. ~8 % crowd regions, 8,552
  detections incl. tied scores and images with more than 100 detections per class) compared per class on AP50, AP75,
  AP50:95, recall@0.50 and mean recall. Maximum absolute difference: **0.0** (evidence
  `artifacts/qa/spike/coco_ap_random_crosscheck.json`). The harness was checked to detect an injected change
  (maxDets 50 instead of 100 gave a difference of 0.1667 and a non-zero exit).
- `crosscheck.py`: rebuilds the ground truth independently from the archive, feeds the *raw service predictions* of a
  run to `COCO.loadRes` / `COCOeval` and compares with the NumPy values. For the release run: 300 images, 13,443 detections fed, maximum
  absolute difference over AP50, AP75, AP50:95, recall@0.50 and mean recall of all nine classes **0.0** (tolerance
  1e-6; `artifacts/qa/spike/c77b30763a37492888f68c3f9e794d6d.crosscheck.json`). The dry run (1511 detections) also
  matched exactly.

## Limitations

- COCO val2017 consists of Flickr photographs, not dash-cam video: viewpoint, object scale, motion blur and compression
  differ from DreamDrive's uploaded videos, so these numbers do not transfer to road footage.
- RF-DETR-N was trained on COCO train2017; val2017 is its standard held-out split (no image overlap), but the taxonomy
  and photographic style are in-domain for RF-DETR and favour it.
- YOLOPv2 `vehicle` (BDD100K-trained, one class) is scored against merged COCO car+bus+truck as a cross-dataset check;
  the datasets use different labelling conventions, so its AP is indicative only. In the ensemble, a YOLOPv2 vehicle
  box that overlaps an RF-DETR bus/truck box (IoU ≥ 0.5) is replaced by it, which lowers `vehicle` recall on buses and
  trucks; `vehicle_any` scores what the app actually draws.
- Scored at the production threshold 0.1: detections below it never reach the app, so the precision–recall curve is
  truncated. The numbers are therefore not comparable with leaderboard AP (computed at threshold ≈0.001).
- 300 images; classes with few instances (stop sign: 16) have wide uncertainty. No confidence intervals are computed.
- Latency is measured on the developer host (Docker Desktop WSL2, CPU, shared with other work); it is a measurement,
  not a guarantee.

## Not evaluated, and why

| Capability | Status | Reason |
|---|---|---|
| Lane-line accuracy | `not_evaluated` | No openly licensed lane labels available; BDD100K requires owner registration |
| Drivable-area IoU | `not_evaluated` | Same as above |
| Traffic-light colour (red/yellow/green) | `not_evaluated` | COCO has no light-state labels; the colour is an HSV heuristic |
| General traffic signs (other than stop sign) | `unsupported` | No verified, licence-clear checkpoint supports them |
| Tracking (IDF1, ID switches) | `not_evaluated` | Needs labelled video with track ids |
| Dash-cam domain detection accuracy | `not_evaluated` | No licensed labelled dash-cam frames; the CC0 fixture clip is unlabelled |
| Decision / reason-code correctness on real video | `not_evaluated` | No labelled ground truth for decisions |
| Leaderboard-protocol AP (score threshold ≈0.001) | not run | The product never sees detections below 0.1; a low-threshold run is possible with `--conf-threshold 0.001` but was not performed |
| CUDA fp16 accuracy | not run | This evaluation used the CPU fp32 image only |

## How to reproduce

Prerequisites: the annotation archive at `datasets/raw/coco/annotations_trainval2017.zip` (SHA256 above), the backend
venv (`backend/.venv`), Docker, and the verified checkpoints under `models/` (see `config/models.resolved.yaml`).

```bash
# 1. (optional) regenerate the manifest; must be byte-identical to the committed file
cd backend
.venv/Scripts/python -m app.evaluation.detector_accuracy build-manifest \
  --annotations ../datasets/raw/coco/annotations_trainval2017.zip --out ../datasets/manifests/coco_val2017_street_v1.json
git diff --exit-code ../datasets/manifests/coco_val2017_street_v1.json

# 2. start the two-model CPU inference service on a private port (layout: see "Run record" below)
docker run -d --rm --name dd-eval -p 127.0.0.1:18031:8001 -v <models dir>:/models:ro <inference image>
curl -s http://127.0.0.1:18031/health/ready

# 3. run the evaluation (downloads up to 300 images into the cache on first use)
.venv/Scripts/python -m app.evaluation.detector_accuracy run \
  --manifest ../datasets/manifests/coco_val2017_street_v1.json \
  --annotations ../datasets/raw/coco/annotations_trainval2017.zip \
  --image-cache ../datasets/raw/coco/val2017_cache \
  --inference-url http://127.0.0.1:18031 \
  --out-dir ../artifacts/evaluations --evidence-dir ../artifacts/qa/spike
docker stop dd-eval

# 4. pycocotools cross-check and results table (from the repository root)
uv run --project tools/eval python -I tools/eval/random_crosscheck.py --trials 20 \
  --out artifacts/qa/spike/coco_ap_random_crosscheck.json
uv run --project tools/eval python -I tools/eval/crosscheck.py \
  --predictions artifacts/qa/spike/<id>.predictions.json --manifest datasets/manifests/coco_val2017_street_v1.json \
  --annotations datasets/raw/coco/annotations_trainval2017.zip --out artifacts/qa/spike/<id>.crosscheck.json
uv run --project tools/eval python -I tools/eval/results_table.py artifacts/evaluations/<id>.json
```

To make the API list a result in a running stack, copy `<id>.json` into the `evaluations` directory of the `app-data`
volume (`DATA_ROOT/evaluations`). Unit tests (no network): `tests/unit/backend/test_coco_ap.py`,
`tests/unit/backend/test_detector_accuracy.py`.
